# Resume Studio 编排架构 v0.1

状态：ACCEPTED  
版本：0.1.0  
日期：2026-08-20

## 1. 决策

Resume Studio 对用户表现为一个顶层编排 Skill：`resume-studio`。用户不需要理解或按顺序手动调用内部能力。

内部采用“编排器 + 专家提供者 + 确定性模块”的混合结构，不把每个步骤都包装成 Skill：

- 需要不同方法论、能产生竞争性表达方案的能力，作为专家 Skill 或 Provider 接入。
- 输入解析、哈希、事实锁定、Schema 校验、分页检查、文件导出等确定性工作，作为脚本或核心模块实现。
- 面试、Offer、贡献证据等非简历改写能力不进入简历方案竞赛，只消费已经确认的最终简历。

此结构兼顾可解释性、可移植性和执行可靠性。嵌套 Skill 的自动发现与跨 Skill 调用并非所有宿主都一致，因此不能依赖“把多个 Skill 文件夹放在一个 Skill 文件夹里”自动完成编排。宿主差异必须由 Adapter 隔离。

## 2. 顶层职责

`resume-studio` 必须：

1. 建立一次申请运行 `run`。
2. 冻结源简历、JD、用户事实库和版式约束。
3. 选择符合任务的专家提供者。
4. 保证所有竞争方案从同一冻结基线独立生成。
5. 将提供者输出规范化为 ChangeSet v0.1。
6. 执行事实、证据、格式和长度门禁。
7. 向 UI 提供可逐段比较的候选建议。
8. 只在用户明确采用后更新工作草稿。
9. 导出最终简历和审计记录。
10. 在最终简历冻结后，才生成面试准备材料。

## 3. 执行阶段与顺序

| 阶段 | 名称 | 类型 | 可并行 | 输出 | 失败处理 |
|---|---|---|---|---|---|
| 0 | `INTAKE` | 确定性模块 | 否 | 原始文件清单 | 缺少简历或 JD 时停止 |
| 1 | `PARSE` | 确定性模块 | 简历/JD 可并行 | Resume AST、JD AST | 解析失败时请求用户补充 |
| 2 | `FREEZE_BASELINE` | 确定性模块 | 否 | baseline hash、事实锁 | 哈希或事实冲突时停止 |
| 3 | `ANALYZE_JOB` | 专家/模块 | 可内部并行 | JD 要求、关键词、风险 | 允许部分结果但必须标记 |
| 4 | `SELECT_PROVIDERS` | 编排器 | 否 | 本轮专家清单 | 没有可用简历专家时停止 |
| 5 | `GENERATE_CANDIDATES` | 专家 Providers | 是 | 原生或待适配输出 | 单个失败不阻断其他专家 |
| 6 | `NORMALIZE` | Adapter | 是 | ChangeSet v0.1 | 无法规范化则降级或拒绝 |
| 7 | `VALIDATE` | 确定性模块 | 是 | 门禁结果 | 事实或安全失败则阻止采用 |
| 8 | `COMPARE_AND_DECIDE` | UI + 用户 | 否 | 用户决策日志 | 不允许静默自动采用 |
| 9 | `COMPOSE_DRAFT` | 确定性模块 | 否 | 工作草稿 | 冲突必须回到用户决策 |
| 10 | `RENDER_AND_QA` | 确定性模块 | 部分 | DOCX/PDF/版式报告 | 一页或版式失败不得交付 |
| 11 | `INTERVIEW_PREP` | 专家 Providers | 是 | 面试材料 | 只能读取最终冻结简历 |
| 12 | `EXPORT_AUDIT` | 确定性模块 | 否 | 审计包 | 审计不完整不得声称完成 |

## 4. 并行不变量

所有参与横向比较的专家必须收到相同的：

- `resumeBaselineHash`
- `jobBaselineHash`
- Resume AST 版本
- JD AST 版本
- 用户事实库快照
- 语言、页数和模板约束

禁止把专家 A 的输出作为专家 B 的输入后，再将 A 与 B 标记为独立候选方案。融合建议是新的派生 ChangeSet，必须记录父 ChangeSet，并由用户单独确认。

## 5. 哪些是专家 Skill

V1 可以维护多个简历专家方向，但单次运行默认选择 3 个、硬上限为 5 个。编排器必须在运行前校验数量，第 6 个不得进入执行队列。专家方向例如：

- ATS/关键词匹配
- STAR/成果表达
- 岗位叙事与模块排序
- 技术项目深度
- 设计/产品叙事
- 风险与证据审计

这些名称描述能力类型，不自动授予重新分发第三方 Skill 的权利。将任何 GitHub Skill 内置到公开仓库前，必须单独检查许可证、来源、版本和再分发条件。

## 6. 哪些不是子 Skill

以下能力应优先使用确定性模块：

- DOCX/PDF 解析与段落 ID 生成
- SHA-256 基线哈希
- JSON Schema 验证
- 事实锁与数字比对
- 操作合并和冲突检测
- Word 字体、Symbol run 和分页 QA
- DOCX/PDF 导出
- 本地版本历史

把这些步骤交给自由生成式 Skill 会降低稳定性，并让相同输入难以复现。

## 7. 宿主适配

顶层流程不依赖 Codex、Claude Code 或 WorkBuddy 的专属路径。宿主 Adapter 负责：

- 发现宿主支持的 Skill。
- 调用或模拟调用专家提供者。
- 传递文件和上下文。
- 处理权限确认、超时、取消和错误。
- 将宿主输出送入统一 Normalizer。

若宿主无法可靠调用另一个已安装 Skill，则该 Provider 必须采用第一方执行器、显式 Adapter 或降级为 `ADVISORY_ONLY`，不得假装已执行。

## 8. 用户可见流程

用户默认只看到：

1. 导入简历与 JD。
2. 选择或接受推荐的优化专家。
3. 等待候选方案生成与校验。
4. 逐段比较、采用、编辑或融合。
5. 查看最终版式并导出。
6. 基于最终简历生成面试准备。

内部阶段、错误和权限必须可展开查看，但不应成为完成主流程的前置知识。

## 9. V1 边界

### 必须

- 本地运行。
- Codex 首个宿主 Adapter。
- 一个顶层 `resume-studio` 调用入口。
- 同源并行候选、结构化 ChangeSet、人工决策、可撤销。
- DOCX/PDF 与审计导出。

### 需要用户确认

- 第三方 Skill 请求联网、Shell 或工作区写权限。
- 将第三方 Skill 加入永久 Registry。
- 将用户新输入保存到长期事实库。

### 禁止

- 自动执行未经检查的 GitHub Skill。
- 自动采用影响锁定事实的建议。
- 让面试 Skill 直接修改最终简历。
- 因某个专家失败而伪造其输出。
- 将总分包装成唯一客观答案。

## 10. 成功标准

- 用户只调用一个顶层 Skill 即可完成主流程。
- 默认 3 个、最多 5 个专家可从同一基线独立输出；超过 5 个时运行必须被阻止。
- 任一修改可追溯到提供者、输入基线、证据和用户决策。
- 同一专家失败不影响其他已成功专家进入比较。
- 确定性门禁失败时，输出不会进入可采用状态。
- 新宿主只需新增 Adapter，不改 ChangeSet 核心语义。
