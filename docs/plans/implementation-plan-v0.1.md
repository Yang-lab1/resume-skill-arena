# Resume Studio 总体实现计划 v0.1

状态：待执行（产品规则已确认）  
面向版本：V1 本地自用版  
计划原则：先证明核心可信闭环，再接入完整 UI、更多专家 Skill 和公开发行能力。

## 1. V1 成功标准

V1 完成时，用户应能：

1. 导入一份源简历和一份目标 JD，系统生成冻结基线，所有专家从同一基线独立工作。
2. 同时运行多个专家方案，任何单个专家失败都不阻断其他方案。
3. 按简历区块查看每项建议的原文、建议文本、理由、事实依据和风险。
4. 逐项选用、拒绝、手动编辑和撤销，最后合成一份用户确认版简历。
5. 阻止没有源简历证据的新事实进入最终简历；不确定内容只能作为待确认项。
6. 本地导出 DOCX/PDF，并通过一页、字体、缺字和版式完整性检查。
7. 在最终简历冻结后生成面试准备内容，且不反向污染简历事实。
8. 首次运行时由系统生成推荐的最小权限方案，用户只做一次统一确认。

## 2. 范围边界

### V1 包含

- Windows 本地运行，优先适配 Codex。
- 一个用户入口 `resume-studio`，内部编排多个专家 Provider。
- 结构化 ChangeSet、事实门禁、方案比较、人工决策、最终导出。
- 内置专家与第三方专家使用同一 Adapter Contract。
- 本地数据、可恢复运行、明确的错误报告。

### V1 暂不包含

- 云端账户、多人协作、在线简历托管或收费体系。
- 同时完整支持所有 Agent 客户端；WorkBuddy、Claude Code 先保留适配接口。
- 任意 GitHub 地址的一键无审查执行。
- 自动替用户决定最终措辞或绕过宿主系统的权限确认。
- 在核心数据模型稳定前制作完整商业化 UI。

## 3. 技术默认值

这些是工程默认值，不需要普通用户配置：

- 核心运行时：Node.js + TypeScript。
- 包管理：npm，降低 Windows 用户额外安装负担。
- Schema 校验：JSON Schema Draft 2020-12 + Ajv。
- 自动测试：Vitest。
- 命令入口：先提供本地 CLI，后续由本地 Web UI 调用同一核心 API。
- UI 候选：React + Vite；进入 UI 阶段前单独完成产品流程和交互原型评审。
- 数据默认保存在当前项目的本地运行目录，不上传云端。
- 单次任务默认启用 3 个专家 Provider，硬上限为 5 个；该限制由核心运行校验执行，UI 只负责提前提示。

采用 CLI 先行不是把产品做成命令行工具，而是先建立 UI 可以稳定依赖的核心能力，避免界面与业务规则互相绑定。

## 4. 依赖关系

```text
已确认规范与 Schema
        ↓
契约校验与事实门禁
        ↓
冻结基线与运行目录
        ↓
Provider 注册、隔离运行与结果归一化
        ↓
决策记录、合成与撤销
        ↓
本地比较 UI
        ↓
DOCX/PDF 渲染和版式 QA
        ↓
面试准备、第三方安装、GitHub 发行
```

UI、导出和第三方安装都不得绕过同一套契约校验与事实门禁。

## 5. 分阶段路线

### P1：契约门禁最小闭环

状态：已完成（2026-08-20）

目标：证明系统能够读取 ChangeSet、执行格式与事实检查，并给出普通人能理解的结果。

交付物：

- TypeScript 项目骨架。
- ChangeSet 与 Skill Manifest 校验器。
- “无简历证据的新事实”语义门禁。
- `validate-changeset` 本地命令。
- 正例、反例和自动测试。

完成门禁：有效样例通过；无证据样例被明确阻断；命令返回稳定退出码和可读错误。

### P2：冻结简历基线

状态：已完成（2026-08-20）

目标：把源简历和 JD 转成所有专家共享的、可追踪的输入。

交付物：

- Resume AST、JD Snapshot、Fact Snapshot。
- 稳定区块 ID、内容哈希和来源定位。
- 运行目录与输入冻结机制。

完成门禁：同一输入重复解析得到稳定 ID；修改源文件后不能冒充旧基线。

### P3：编排器与 Provider 运行

状态：已完成（2026-08-20）

目标：从同一冻结基线运行多个专家，并隔离失败。

交付物：

- Provider Registry、运行状态机和超时/失败隔离。
- Codex Adapter。
- 一个内置参考 Provider 和一个模拟失败 Provider。
- 统一日志与可恢复运行记录。

完成门禁：至少两个候选从同一基线产生；一个失败时另一个仍完成；所有结果先过 P1 门禁。

### P4：人工决策与合成

状态：已完成（2026-08-21）

目标：让用户拥有最终控制权，并留下可撤销、可追踪的选择记录。

交付物：

- Decision Log、逐项采用/拒绝/编辑模型。
- 冲突检测、合成器和撤销机制。
- 最终简历的来源追踪。

完成门禁：任何最终文本都能追溯到源文本、专家建议或用户编辑；改变选择可稳定重算。

### P5：本地比较 UI

目标：把核心闭环变成不需要理解技术术语的可视化工作台。

进入条件：P1–P4 的数据契约稳定。UI 设计开始前先完成 design brief、关键流程和低保真原型评审。

首版核心页面：

- 新建任务：选择简历、JD 和推荐专家组合。
- 运行进度：展示正在分析、已完成、已跳过，不暴露底层命令。
- 逐段比较：原文固定在左侧，候选方案横向比较。
- 最终编辑：查看已采用内容、手动修改和撤销。
- 导出检查：用通俗语言展示阻断项和修复建议。

完成门禁：用户无需编辑配置文件或输入命令，即可完成一次比较、选择和合成。

### P6：渲染、导出与面试准备

目标：形成可投递文件，并使面试内容严格基于最终版本。

交付物：

- DOCX/PDF 导出。
- 一页、字体、乱码、缺字、分页和内容完整性 QA。
- 面试问题、回答要点和事实提醒。

完成门禁：导出文件可打开且通过 QA；面试内容引用最终简历版本 ID。

### P7：第三方专家与权限预审

目标：允许用户添加新专家，同时保持低打扰和安全边界。

交付物：

- GitHub URL、本地目录、ZIP 的导入入口。
- 来源、许可证、脚本、权限和契约预审。
- 系统自动生成推荐最小权限包。
- 一键“启用推荐方案 / 跳过”，高级详情可展开。

完成门禁：未通过审查的专家不能执行；拒绝额外权限只跳过该专家，不中断主流程。

### P8：公开发行

目标：让其他用户能够找到、理解、安装、升级和卸载项目。

交付物：

- GitHub README、快速开始、演示数据和故障排查。
- 版本化 Schema、迁移策略和变更日志。
- Codex 安装说明；其他客户端使用独立 Adapter 文档。
- 第三方许可证与固定 revision 清单。

完成门禁：在一台干净 Windows 环境按 README 可完成安装和演示闭环。

## 6. 验证策略

| 层级 | 主要验证 |
| --- | --- |
| Schema | 正例通过、缺字段失败、未知版本失败 |
| 事实门禁 | 无证据新事实必定阻断，措辞优化可通过 |
| 基线 | 区块 ID 与哈希稳定，篡改可检测 |
| 编排 | 并行同源、超时、单 Provider 失败隔离 |
| 决策 | 采用、拒绝、编辑、冲突与撤销可重放 |
| UI | 关键路径真实浏览器测试、键盘可用性、错误恢复 |
| 导出 | Word/PDF 可打开、一页、字体、乱码和分页检查 |
| 安装 | 隔离环境从零安装、升级与卸载 |

## 7. 必须停止并汇报的情况

- 建议内容无法找到可靠的简历证据，却会改变候选人的事实陈述。
- 第三方专家许可证或再分发权不明确，准备进入公开内置清单。
- 需要扩大联网、Shell 或文件访问范围，且超出系统已生成的推荐权限包。
- 宿主 Agent 的能力不足以保证隔离、超时或可恢复运行。
- 导出结果无法稳定满足一页和版式门禁。

## 8. 近期执行顺序

1. P1 契约门禁、P2 冻结基线、P3 Provider 编排与 P4 人工决策合成已经完成。
2. 下一步执行 P5：先完成 design brief、关键流程和低保真原型评审，再实现本地比较 UI。
3. P5 只调用 P1–P4 已验证的核心 API，不在界面层复制事实、数量或合成规则。
